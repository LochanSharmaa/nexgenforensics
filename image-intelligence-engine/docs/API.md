# API Design — Revision 2

Companion to [ARCHITECTURE.md](ARCHITECTURE.md) and
[DATA_MODEL.md](DATA_MODEL.md).

**API-first is a hard rule.** Every capability is a documented REST endpoint,
and no consumer gets a privileged path into the core. That is what lets the
NexGen iMATCH workspace — which reaches these routes through a proxy in
`imatch_api`, keeping the browser on one origin — integrate without refactoring
the platform. Enforced by an architecture test asserting routers contain no
business logic.

- Base path `/api/v1`. Versioned from day one; breaking changes mint `/v2`.
- OpenAPI 3.1 generated by FastAPI, served at `/api/docs`.
- Auth: JWT bearer. Single-user local deployment still authenticates, so the
  multi-user path is exercised from day one rather than bolted on.
- All list endpoints: `?limit=&cursor=&sort=`. Cursor pagination, because offset
  pagination drifts while a pipeline is actively inserting rows.
- Errors: RFC 9457 `application/problem+json`, with a stable `type` slug.

---

## 1. Conventions that encode the design principles

### 1.1 Confidence is never returned bare

Any response carrying `confidence` carries `confidence_explanation` in the same
object. There is no endpoint, projection or query parameter that returns one
without the other. This makes ARCHITECTURE §9.2 an API guarantee rather than a UI
convention.

### 1.2 AI output always carries "Why?"

Any response containing AI-derived content carries an `explanation` object
referencing supporting evidence ids. Content without it is a bug, not a degraded
mode.

### 1.3 Evidence is always reachable in one hop

Every object that asserts something exposes `evidence_url` — a link to its full
chain. No client has to know how to assemble provenance.

## 2. Investigations

```http
POST   /api/v1/investigations
GET    /api/v1/investigations
GET    /api/v1/investigations/{id}
PATCH  /api/v1/investigations/{id}
DELETE /api/v1/investigations/{id}          # soft; honours retention policy
POST   /api/v1/investigations/{id}/archive
```

`POST` requires `lawful_basis`; omitting it is a `422` and the refusal itself is
written to the audit log.

```jsonc
// POST /api/v1/investigations
{ "case_id": "OSINT-2026-114", "title": "Provenance of supplied photograph",
  "lawful_basis": "Client engagement 2026/114", "purpose": "Establish first publication",
  "jurisdiction": "IN", "retention_days": 365 }
```

### 2.1 Images and pipeline control

```http
POST   /api/v1/investigations/{id}/images          # multipart upload
GET    /api/v1/investigations/{id}/images
GET    /api/v1/images/{image_id}
GET    /api/v1/images/{image_id}/relationships     # provenance edges
GET    /api/v1/images/{image_id}/appearances

POST   /api/v1/investigations/{id}/runs            # start / resume pipeline
GET    /api/v1/investigations/{id}/runs
GET    /api/v1/runs/{run_id}
POST   /api/v1/runs/{run_id}/pause
POST   /api/v1/runs/{run_id}/resume
GET    /api/v1/runs/{run_id}/stages
```

`POST /runs` on an investigation with a partially-complete run **resumes at the
first non-OK stage** rather than restarting. Re-running paid discovery because a
later stage crashed is both wasteful and non-reproducible.

### 2.2 Live progress

```http
GET    /api/v1/runs/{run_id}/events            # text/event-stream (SSE)
```

SSE over WebSocket: traffic is one-directional, SSE reconnects natively, and it
survives proxies that mishandle upgrade headers.

```
event: stage
data: {"stage":"CRAWL","status":"RUNNING","items_done":14,"items_total":37}

event: stage
data: {"stage":"CRAWL","status":"OK","items_done":37,"items_failed":2}
```

## 3. Sources — the Source Explorer contract

```http
GET    /api/v1/investigations/{id}/pages
GET    /api/v1/pages/{page_id}                 # full source profile
GET    /api/v1/pages/{page_id}/screenshot      # 302 → signed object-store URL
GET    /api/v1/pages/{page_id}/html            # archived snapshot
GET    /api/v1/pages/{page_id}/facts
GET    /api/v1/pages/{page_id}/entities
GET    /api/v1/pages/{page_id}/images
GET    /api/v1/pages/{page_id}/links
GET    /api/v1/pages/{page_id}/related         # content-cluster siblings
GET    /api/v1/investigations/{id}/domains
GET    /api/v1/investigations/{id}/clusters
```

`GET /pages/{id}` returns the whole Source Explorer payload — title, URL,
screenshot and HTML references, extracted facts, entities, outbound links,
images, archive links, timeline position, related pages. One request, because
the UI screen is one screen.

## 4. Evidence — the Evidence Explorer contract

```http
GET    /api/v1/investigations/{id}/facts       # ?status=&entity_id=&attribute=
GET    /api/v1/facts/{fact_id}
GET    /api/v1/facts/{fact_id}/evidence-chain  # ← the traceability guarantee
GET    /api/v1/observations/{observation_id}
GET    /api/v1/investigations/{id}/entities
GET    /api/v1/entities/{entity_id}
GET    /api/v1/entities/{entity_id}/facts
POST   /api/v1/entities/{entity_id}/split      # investigator corrects over-merge
POST   /api/v1/entities/merge                  # investigator corrects under-merge
```

```jsonc
// GET /api/v1/facts/{id}/evidence-chain
{
  "fact": { "attribute": "employer", "value": "Meridian Logistics",
            "status": "COMMON", "confidence": "MEDIUM", "confidence_score": 0.58,
            "confidence_explanation": {
              "factors": [
                { "factor": "independent_domains", "observed": 2, "contribution": 0.30,
                  "why": "Asserted by 2 unrelated registrable domains" },
                { "factor": "extraction_method", "observed": "SCHEMA_ORG",
                  "contribution": 0.20,
                  "why": "One source published this as machine-readable schema.org data" }
              ],
              "ceiling_reason": null } },
  "chain": [
    { "observation_id": "…", "method": "SCHEMA_ORG", "raw_value": "Meridian Logistics",
      "char_start": 1204, "char_end": 1222, "extractor_version": "extract@2.1.0",
      "extracted_at": "2026-08-03T09:14:22Z",
      "page": { "id": "…", "url": "https://…/leadership", "title": "Leadership",
                "registrable_domain": "meridianlogistics.example",
                "domain_classification": "COMPANY",
                "fetched_at": "2026-08-03T09:13:58Z",
                "screenshot_url": "/api/v1/pages/…/screenshot",
                "html_url": "/api/v1/pages/…/html" },
      "content_cluster": { "id": "…", "role": "ORIGINAL" } }
  ],
  "conflicts": []
}
```

Manual `split` / `merge` write to `entities` and are audited, but they **never**
touch `observations`. Correcting a resolution error must not rewrite what a page
actually said.

## 5. Graph, timeline, monitoring

```http
GET    /api/v1/investigations/{id}/graph        # ?node_types=&depth=&root=
GET    /api/v1/graph/nodes/{node_id}
GET    /api/v1/graph/nodes/{node_id}/neighbours
GET    /api/v1/graph/edges/{edge_id}/evidence

GET    /api/v1/investigations/{id}/timeline     # ?from=&to=&kinds=
GET    /api/v1/timeline/{event_id}

POST   /api/v1/investigations/{id}/monitors
GET    /api/v1/investigations/{id}/monitors
PATCH  /api/v1/monitors/{monitor_id}
DELETE /api/v1/monitors/{monitor_id}
GET    /api/v1/monitors/{monitor_id}/runs
GET    /api/v1/monitors/{monitor_id}/changes
```

Every graph edge response includes `derivation` and
`evidence_observation_ids`. Every timeline event includes `precision`, so no
client can render an inferred date as exact.

## 6. Notebook and bookmarks

```http
POST   /api/v1/investigations/{id}/notes
GET    /api/v1/investigations/{id}/notes        # ?tags=&q=
PATCH  /api/v1/notes/{note_id}
DELETE /api/v1/notes/{note_id}
POST   /api/v1/notes/{note_id}/links            # cite evidence from a note
POST   /api/v1/notes/{note_id}/attachments

POST   /api/v1/investigations/{id}/checklists
PATCH  /api/v1/checklist-items/{item_id}

POST   /api/v1/investigations/{id}/bookmarks
GET    /api/v1/investigations/{id}/bookmarks
DELETE /api/v1/bookmarks/{bookmark_id}
```

There is deliberately **no endpoint** that writes human content into
`observations` or `facts`. Notes cite evidence; they never become it.

## 7. Copilot

```http
POST   /api/v1/investigations/{id}/copilot/sessions
POST   /api/v1/copilot/sessions/{session_id}/messages
GET    /api/v1/copilot/sessions/{session_id}/messages
```

```jsonc
// response
{ "role": "assistant",
  "content": "Two sources place the subject at Meridian Logistics [e1][e2], but one 2024 profile lists a different employer [e3].",
  "citations": { "e1": "obs_…", "e2": "obs_…", "e3": "obs_…" },
  "validation_status": "PASSED",
  "rejected_spans": [],
  "explanation": { "basis": "3 observations across 3 registrable domains",
                   "conflict_group_id": "…" } }
```

The copilot's tools are **read-only and investigation-scoped**. It has no web
access and no write path. Output is validated after generation: every cited id
must exist and support its claim's subject, and failing sentences are returned as
`rejected_spans` rather than silently rendered. `validation_status: REJECTED`
is a normal, persisted outcome — the assistant's failures are auditable too.

## 8. Search, reports, audit, providers

```http
GET    /api/v1/search                  # ?q=&types=&investigation_id=&from=&to=
GET    /api/v1/search/by-image-hash    # ?sha256= | ?phash=&max_distance=

POST   /api/v1/investigations/{id}/reports     # {"format":"PDF"}
GET    /api/v1/investigations/{id}/reports
GET    /api/v1/reports/{report_id}/download

GET    /api/v1/investigations/{id}/audit
GET    /api/v1/investigations/{id}/audit/verify   # re-walks the hash chain

GET    /api/v1/providers                # manifests, capabilities, config state
POST   /api/v1/providers/{name}/test    # credential check
```

`GET /providers` reports each plugin as `configured`, `unconfigured`, or
`failing` — distinctly. "No matches" and "no API key" lead to opposite next
steps, and conflating them puts a false negative into a report.

`GET /audit/verify` returns `{valid, records, broken_at, reason}`.

---

## 9. Rate limits and safety

- Upload: 20 MB per image, MIME sniffed not trusted from the header.
- Crawl politeness is server-side per registrable domain and is **not**
  client-controllable.
- Server-side URL fetching is only ever performed by the hardened fetcher
  (SSRF-vetted, per-hop redirect revalidation). No endpoint proxies an arbitrary
  client-supplied URL.
